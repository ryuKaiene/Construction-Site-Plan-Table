# AIラボ（Claude Pro余剰リソース活用プロジェクト）レビュー・システム仕様・ロードマップ

作成日: 2026-11-11 ／ 状態: 提案（未承認）

---

## 0. 結論（先に要点）

1. **構想は実現可能。ただし「完全自律」ではなく「半自律」が現実解。** テーマ発見と提案は自動化できるが、開発は承認後の対話セッションで行うのが品質・安全・利用枠のすべてで有利。
2. **本当のボトルネックはClaudeの利用枠ではなく、あなたのレビュー時間と現場への定着。** 毎週1つ新しい成果物を作ると、半年で20個以上の「誰も使わない・誰も保守しない道具」が残る。目的関数を「枠の消化」でも「成果物の数」でもなく **「2週間後も使われている成果物の数」** に置き換えるべき。
3. **毎週ゼロから10テーマを生成する方式はやめ、永続バックログ方式にする。** 候補は蓄積・採点・更新し、毎週その上位10件を提示する。重複防止・評価の反映・利用枠の節約が同時に解決する。
4. **新規開発は月1〜2本に抑え、残りの週は既存成果物の育成に充てる**（配分の目安：育成7・新規2・探索1）。
5. **最大のリスクは実行場所の未確定。** Obsidian保管庫とNotebookLM連携はおそらくあなたのPC上にあり、クラウド上のClaude Codeセッションからは見えない（本セッションでも両方とも接続されていないことを確認）。どこで動かすかを最初に決める必要がある。

## 1. 構想レビュー（8つの検討項目）

### 1-1. 本当に実現可能か

| 要素 | 判定 | 補足 |
|---|---|---|
| 週次のテーマ提案 | ○ | 技術的には容易。質は入力情報（メモ・会議記録）の質で決まる |
| 承認後の実装 | ○ | すでにこのリポジトリ（工程表アプリ）で実績のある進め方 |
| Obsidianへの記録 | ○ | 専用フォルダへの追記のみなら安全 |
| 評価の反映 | ○ | 評価を構造化して保存すれば可能。自由文だけだと反映が曖昧になる |
| 完全無人での実行 | △ | 定期実行は可能だが、PCの起動状態・認証・連携の安定性に依存 |
| 利用枠残量の自動取得 | △ | 公式な取得手段は確認できていない。推定と手動確認の併用になる（1-2参照） |
| NotebookLM連携の安定運用 | △ | 非公式連携の可能性が高く、突然動かなくなる前提で代替経路が必要 |

### 1-2. 利用枠を有効活用する最適な仕組み

**指摘：** 「余った枠を使い切る」発想は、価値の低い作業を生む誘因になる。構想の9章でも自戒されているが、仕組みとして防ぐ必要がある。

**提案：**

- **作業を3層に分ける。**
  - 必須層：週次の提案（軽い）
  - 本体層：承認されたテーマの実装
  - 余力層：テスト追加・マニュアル作成・別案検証・既存成果物の改善（あらかじめ「余力キュー」に積んでおき、枠が残っているときだけ消化）
- **週次リセットの1〜2日前を「余力消化日」とする。** リセット直後は通常業務用に枠を温存し、リセット直前に余力キューを実行する。これが余剰枠の活用として最も合理的。
- **残量の把握：** 対話画面の `/usage` であなたが見た数値を一言伝える方式を基本とする（例：「週間42%」）。自動取得はPhase 3で検証項目とする。取得できない場合は、セッション数と作業規模から推定し、推定であることを記録に明記する。
- **5時間枠への対処：** 大きな開発は1セッションで完結させず、「設計→実装→検証」を別セッションに分割し、各セッション終了時に引き継ぎメモを残す。
- **モデルの使い分け：** 情報収集・要約・整形は軽量モデル、判断・設計・難しい実装のみ上位モデル。これだけで消費は大きく変わる。

### 1-3. NotebookLMとClaude Codeの役割分担

**方向性は正しい。ただし3点修正する。**

1. **NotebookLMに任せるのは「外部の大量資料」に限定する。** 共通仕様書、積算基準、法令・通達、メーカー資料、過去の施工計画書など。Obsidianのメモは量が小さく頻繁に変わるため、Claude側で差分だけ読む方が速く確実。
2. **NotebookLMの回答は「根拠付きの下調べ」として扱い、最終判断の根拠にしない。** 数量・基準値・法的要件は必ず出典箇所を確認する。建設業では誤った基準値がそのまま事故・手戻りにつながる。
3. **代替経路を用意する。** 連携が切れた場合は、資料をテキスト化してリポジトリに置き、軽量モデルの補助エージェントに読ませる。

| 作業 | 担当 |
|---|---|
| 大量資料の読み込み・横断検索・要約 | NotebookLM |
| メモ・会議記録の差分読み取り | Claude（軽量モデル） |
| テーマの採点・選定・設計判断 | Claude（上位モデル） |
| 実装・テスト | Claude Code |
| 最終的な採否・現場での試用・評価 | あなた |

### 1-4. Obsidian連携

**指摘：** 毎週保管庫全体を読むのは枠の浪費であり、メモが増えるほど悪化する。また「既存データを変更しない」を口約束ではなく構造で保証すべき。

**提案：**

- **書き込みは専用フォルダ1つに限定**（仮称 `AI-Lab/`。既存の命名規則に合わせて変更可）。それ以外は読み取り専用とし、Claude Codeの権限設定で専用フォルダ外への書き込みを拒否する。
- **差分読み込み：** 前回実行以降に更新されたメモだけを読む。
- **「理解の要約」を1枚持つ：** あなたの関心・進行中案件・繰り返し出る課題をまとめた `プロフィール.md` を保持し、毎週差分で更新する。次回以降はこの1枚＋差分だけ読めば足りる。内容はあなたが読んで訂正できる。
- **会議記録を課題発見の主要な情報源に加える。** すでに社長との毎日の1on1記録があり、Plaud（録音）・Gmail・カレンダー・Driveも接続されている。メモに書かれるのは「すでに自覚した課題」だが、会議記録には **「繰り返し話題になるのにまだ手を打っていない問題」** が現れる。これが構想2章の「自分が気づいていない課題」の最良の供給源になる。

### 1-5. 毎週自律的にテーマを発見する仕組み

**指摘：** 毎週10個を新規生成し、7項目ずつ書かせると、3〜4週目から水増し・言い換えが始まる。「過去と重複しない」という条件が、良いテーマの再提案（状況が変わって今なら価値がある）まで禁じてしまう。

**提案：永続バックログ方式**

1. **収集**：メモ差分・会議記録・メール件名傾向・既存成果物の評価から「課題の兆候」を拾う
2. **候補化**：兆候をバックログ（1テーマ1ファイル）に追加、既存候補には証拠を追記
3. **採点**：下記の式で点数化
4. **提示**：上位10件を一覧表で提示。上位3件のみ7項目を詳述、残り7件は1行ずつ
5. **推薦**：1件を理由付きで推薦

**採点式：** `点数 = (頻度 × 影響 × 確度) ÷ 作業量 × 領域の重み`

- 頻度：その課題が記録に現れた回数（証拠の件数）
- 影響：削減できる時間／関わる人数
- 確度：実現可能性と、現場で実際に使われる見込み
- 作業量：セッション数で見積もる（S=1、M=2〜3、L=4以上）
- 領域の重み：設定ファイルで指定（1-6の拡張設計）

**候補の状態：** `候補 → 提示済 → 採用／保留／却下（理由つき）`。却下理由は必ず残し、同種の提案を抑制する。保留は状況が変われば再提示してよい。

**証拠の明示：** 各テーマに「どの記録のどの記述から導いたか」を必ず付ける。根拠のない思いつきは「探索枠」として区別し、10件中2件までとする。

### 1-6. 成果物を継続的に育てる仕組み

**成果物台帳と段階管理：**

| 段階 | 意味 | 次へ進む条件 |
|---|---|---|
| 試作 | 動くものができた | あなたが実際に1回使う |
| 試用 | 実業務で試している | 2週間後も使っている |
| 定着 | 業務に組み込まれた | — |
| 保守 | 変更は不具合対応のみ | — |
| 廃止 | 使われなくなった | 理由を記録し、学びをプロフィールへ |

**運用ルール：**

- **同時に「試用」段階に置けるのは3件まで。** 超える場合は新規開発を止め、既存の定着か廃止を先に決める。
- **週の配分の目安：** 育成7・新規2・探索1。試用中の成果物があれば、その改善が新規テーマより優先。
- **評価は30秒で済む形式にする。** 5段階の点数＋「使ったか（はい／いいえ）」＋一言。長文を求めると評価自体が続かない。評価が2週間ない場合は「使われていない」とみなして確認する。
- **低評価の分析：** 原因を「課題設定の誤り／解決方法の誤り／使い勝手／導入の手間／時期尚早」に分類して記録し、採点の「確度」に反映する。
- **技術の標準化：** 成果物ごとに技術がばらつくと保守不能になる。原則として本リポジトリと同じ構成（Cloudflare Pages＋Functions＋D1、ビルド不要の素朴なHTML/JS）に揃え、表計算で済むものは表計算にとどめる。

### 1-7. 技術構成

```
[情報源]                         [頭脳・実行]                  [記録・成果物]
Obsidian保管庫（読取専用） ─┐
1on1記録・Plaud録音       ─┤     Claude Code
Gmail・カレンダー・Drive   ─┼──▶  ├ 週次提案スキル      ──▶  Obsidian: AI-Lab/（書込専用領域）
成果物の評価              ─┤     ├ 開発スキル           ──▶  GitHub: 成果物ごとのリポジトリ
NotebookLM（外部資料）    ─┘     ├ 記録スキル           ──▶  Cloudflare: 公開先（承認後）
                                 └ 評価取込スキル
                                 設定: 領域の重み・権限・予算
```

**構成要素：**

- **AIラボ用リポジトリ（非公開・新規）**：スキル定義、設定、バックログ、成果物台帳を置く。現在の工程表リポジトリとは分離する（本書は暫定的にここへ置いている）。
- **スキル4本**
  - `weekly-discover`：収集→バックログ更新→採点→上位10件と推薦を提示
  - `weekly-build`：承認されたテーマを設計→実装→検証
  - `weekly-record`：開発記録をObsidianに作成、台帳を更新
  - `feedback`：評価を取り込み、バックログの点数とプロフィールを更新
- **設定ファイル `scope.yaml`**（領域の拡張・優先度変更はここだけで行う）

```yaml
domains:
  業務効率化:   { weight: 1.0, enabled: true }
  新規事業:     { weight: 0.3, enabled: true }
  家族・家庭:   { weight: 0.0, enabled: false }
  技術研究:     { weight: 0.0, enabled: false }
  自己成長:     { weight: 0.0, enabled: false }
  趣味・生活:   { weight: 0.0, enabled: false }
allocation: { grow: 0.7, new: 0.2, explore: 0.1 }
limits:     { trial_products_max: 3, explore_slots: 2 }
```

  「来月は家庭も2割入れて」と指示されれば、Claudeがこのファイルを書き換える。複数領域の並行は重みで自然に実現でき、領域ごとに提案枠を固定することもできる。

- **Obsidian側の構成（専用フォルダ内のみ）**

```
AI-Lab/
├ プロフィール.md          … あなたの関心・課題の要約（差分更新）
├ 週次/2026-W46.md         … 候補10件・選定・成果物・評価・次回改善
├ バックログ/<テーマ>.md    … 1テーマ1ファイル（状態・点数・証拠）
├ 成果物/<名称>.md          … 台帳（段階・保存場所・技術・評価履歴）
└ 余力キュー.md            … 枠が余ったときにやる作業
```

  週次ノートは構想7章の記録項目9つをそのまま見出しにしたテンプレートで作成する。

- **権限設定**：専用フォルダ外への書き込み拒否、メール送信・公開・課金を伴う操作は常に確認を要求。

### 1-8. 不足している機能とリスク

| # | 不足・リスク | 対策 |
|---|---|---|
| 1 | **実行場所が未定義**（PCかクラウドか） | Phase 0で決定。2章参照 |
| 2 | **機密情報の扱い**：1on1記録には人事・人員・取引先の情報が含まれる | 成果物・公開リポジトリに実名や案件名を持ち出さない規則を明文化。NotebookLMへ登録する資料の範囲も決める |
| 3 | **成功指標がない** | 「2週間後の継続利用数」「削減時間の自己申告」「採用率」を週次ノートに記録 |
| 4 | **保守負債**：成果物が増えるほど維持が重くなる | 試用3件上限、技術の標準化、廃止の明文化 |
| 5 | **社員への展開**：役員個人の道具と全社の道具では難易度が桁違い | テーマごとに「利用者は誰か」を必須項目にする。当面は自分が利用者のものを優先 |
| 6 | **承認の待ち時間**：提示しても見てもらえなければ止まる | 提示は月曜朝に1画面で読める量。未回答なら育成作業のみ進める |
| 7 | **評価の形骸化** | 30秒評価、無評価2週間で確認 |
| 8 | **連絡自動化（メール・LINE）の誤送信** | 下書き作成までを自動、送信は常に人が行う。LINEは公式アカウントの費用・規約確認が前提 |
| 9 | **終了条件がない**：何をもって完成とするか | テーマ承認時に「完成の定義」を1〜3行で合意 |
| 10 | **AIの思い込み**：プロフィールが誤ったまま固定化する | プロフィールは月1回あなたが目を通す |

## 3. 改訂版の週次サイクル

| 曜日の目安 | 内容 | 自動／手動 |
|---|---|---|
| 月曜朝 | `weekly-discover`：差分収集→バックログ更新→上位10件＋推薦を週次ノートに作成 | 自動（Phase 3以降）／それまでは一言で起動 |
| 月曜 | あなたが承認（番号で返答）。「完成の定義」を合意 | 手動（1〜2分） |
| 火〜木 | `weekly-build`：設計→実装→検証。セッション分割 | 対話 |
| 木〜金 | `weekly-record`：記録作成、成果物を渡す | 自動 |
| 随時 | 評価（30秒）→ `feedback` | 手動 |
| リセット前日 | 余力キューの消化 | 自動または一言で起動 |

影響の大きい操作（既存ファイル変更・外部送信・費用発生・公開）は、どの段階でも事前承認を必須とする。

## 4. 実装ロードマップ

### Phase 0：前提の確定（1週目・1セッション）
- 2章の決定事項を確定
- AIラボ用リポジトリ作成、`AI-Lab/` フォルダと各テンプレート作成
- 権限設定（書き込み範囲の制限）
- **完了条件：** 保管庫の読み取りと専用フォルダへの書き込みが動作確認できている

### Phase 1：最小構成で1周回す（2〜3週目）
- `プロフィール.md` 初版作成（保管庫の初回分析。ここだけは重い作業）
- `weekly-discover` と `weekly-record` を実装
- 手動起動で1サイクル実施し、最初の成果物を1つ作る
- **完了条件：** 週次ノート1枚と、あなたが実際に使った成果物1つ

### Phase 2：育成の仕組み（4〜6週目）
- 成果物台帳、段階管理、`feedback` スキル
- 採点式に評価を反映、却下理由による抑制
- 会議記録（1on1・Plaud）を情報源に追加
- **完了条件：** 評価が次週の提案順位に反映されていることを確認できる

### Phase 3：半自律化と枠の最適化（7〜10週目）
- 週次提案の定期実行（提示まで無人）
- 余力キューとリセット前日の消化
- 利用枠残量の自動取得の可否を検証（不可なら手動申告を正式運用とする）
- NotebookLMの代替経路整備
- **完了条件：** 4週連続で、月曜朝に提案が届いている

### Phase 4：領域の拡張（3か月目以降・あなたの判断で）
- `scope.yaml` で他領域を有効化
- 領域ごとの提案枠、複数テーマの並行
- 四半期ごとの振り返り（定着数・廃止数・削減時間）

## 5. 当初構想からの主な変更点

| 当初構想 | 改訂案 | 理由 |
|---|---|---|
| 余剰枠の有効活用が目的 | 定着した成果物の数が目的、枠は制約条件 | 消化が目的化するのを防ぐ |
| 毎週10テーマを新規生成 | 永続バックログから上位10件を提示 | 水増し防止、重複管理、枠の節約 |
| 10件すべてに7項目 | 上位3件は詳述、残りは1行 | 読む負担と生成コストの削減 |
| 毎週1つ新規開発 | 育成7・新規2・探索1、試用は3件まで | 保守負債と使われない成果物の防止 |
| 過去の提案と重複させない | 却下は抑制、保留は再提示可 | 状況変化で価値が出るテーマを拾う |
| Obsidianを毎週分析 | プロフィール1枚＋差分 | 枠の浪費を防ぐ |
| 情報源はObsidian中心 | 会議記録・メール・予定を追加 | 未自覚の課題は会話に現れる |
| NotebookLMを積極活用 | 外部の大量資料に限定、代替経路あり | 連携の不安定さと検証可能性 |
| 利用枠を考慮して調整 | 3層構造＋リセット前日の余力消化 | 残量が取れなくても機能する設計 |
